2. Service scope and categories of data

Cesena Remembers is an educational mobile application and website about the history of Cesena. It provides an interactive map, guided tours, location-based features, quizzes, XP, achievements, a global leaderboard, public profiles, friend requests, user blocking and profile reporting, and push notifications. The current app does not integrate Firebase Analytics/Google Analytics or advertising SDKs.

  • Account and authentication: Firebase UID, email address and information associated with Google Sign-In and Firebase Authentication.
  • Legal acceptance and age declaration: server-generated timestamps and version identifiers for the accepted Terms, acknowledged Privacy Notice and self-declared minimum-age policy.
  • Profile and game progress: display name, username, avatar, XP, completed tours, visited points of interest, quiz results, achievements and statistics.
  • Social features: friend requests, accepted friendships, block lists and the identifiers needed to maintain those relationships.
  • User reports: reporter and reported-account UIDs, the reported display-name or username field, a snapshot of the profile values at report time, the selected reason, optional details, creation time and review status. Reports are stored in the private Firestore collection user_reports and are not readable by app clients.
  • Location and device: GPS coordinates while the relevant operating-system permission and in-app preference are enabled; app version, device information, IP address and technical request logs.
  • Notifications: FCM registration token, notification preference, consent timestamp and language preference, if the user opts in.
  • Diagnostics: optional Crashlytics reports, only after an explicit in-app choice. They may contain stack traces, exception type, app/device technical information, Crashlytics Installation UUID and Firebase Installation ID.
  • Moderation: block entries are stored in user_blocks and contain the blocking and blocked account UIDs and creation time. For a banned account, UID, reason and ban date are stored separately in banned_users.

The app is not designed to collect special-category data, contacts, photos or chat messages.

4. GPS, maps and routes

When location permission is granted and the in-app GPS preference is enabled, the app reads the device's location to show the user's position, calculate distance to a stop and detect arrival. During an active tour, the app automatically refreshes the route to the current stop. The device's current coordinates and the destination coordinates are sent to Mapbox Directions whenever the location changes by approximately 40–45 metres or the destination changes. This happens automatically; the user does not need to request each update.

Map tile requests also disclose the IP address, requested tile URL or coordinates and ordinary technical request data to the relevant provider. The app uses CARTO for the standard map, Stadia Maps for the dark map (Alidade Smooth Dark), and Mapbox for satellite imagery (Mapbox Satellite). Satellite tile requests disclose the IP address, requested tile URLs/coordinates and technical request metadata to Mapbox; the project's public Mapbox token is included in each request. The approximate area being viewed can be inferred from the requested tiles. Stadia tile requests use its EU map endpoints (`tiles-eu.stadiamaps.com`), which the provider says connect clients to servers in Frankfurt and Paris and scrub personal data at the network edge. Walking routes returned by Mapbox Directions are attributed directly on the map and in the Credits section. A continuous GPS history is not stored in the Firestore profile. Game progress may record visited places and completed stops.

5. Public profiles, leaderboard and social features

Basic public profiles and the global leaderboard can be queried by any authenticated account, not only reciprocal friends. They may show display name, username, avatar, XP, friend count and completed-tour count. Detailed statistics are restricted to the account owner and reciprocal friends under the app's access rules. Use a nickname: do not include your full name, date of birth, school, address, phone number, email address or other identifying details. Other authenticated users, including minors, may view public profile information.

6. Quizzes, backend and language model provider

A quiz request contains the point-of-interest identifier, place name and description, current XP, language and an Authorization: Bearer Firebase Authentication ID token. The token identifies the user through its UID and may contain an email address and other profile-related claims (such as a display name) where available. The server validates the signature, issuing project, expiry and account status (disabled or token revoked), then uses the UID for per-user rate limiting and deduplication of simultaneous requests. The Google/Firebase password is not sent to the quiz backend. The place name and description supplied by the client are not used to construct the model prompt: the backend uses its own POI allowlist and historical fact sheets. The token and its identity claims are not forwarded to GroqCloud. The server also receives the source IP address and technical request data. Requests to https://pascal.ispascalcomandini.it:8000 use HTTPS/TLS and the app trusts the server certificate bundled with the app.

The backend uses historical fact sheets maintained on the server to build a prompt for GroqCloud. The prompt contains the place facts, language and difficulty derived from XP. The Firebase ID token, UID, email address and other authentication claims are not forwarded to GroqCloud. The provider nevertheless receives the prompt content and server connection metadata. The project does not declare a dedicated Zero Data Retention configuration. According to the provider's published information, inference inputs and outputs are not retained by default but may be temporarily retained for reliability or abuse investigations for up to 30 days; usage metadata is collected. Generated quizzes may contain errors or omissions.

7. Firebase, push notifications, diagnostics and App Check

7.1 Authentication, Firestore and Cloud Messaging

Firebase Authentication manages sign-in through Google Sign-In. Cloud Firestore stores accounts, profiles, usernames, social relationships, progress and statistics. Firebase Cloud Messaging (FCM) delivers optional push notifications. Notifications are off by default: they are enabled only after the user expressly turns on the in-app notification option and grants the operating-system permission. The app records the consent state and a server-side timestamp. Legacy accounts without that consent record remain opted out. When the user withdraws consent or disables notifications, the app removes the token from the profile and deletes the local FCM token. The notification microservice listens in real time to the users collection without a field projection. Firestore therefore delivers complete document snapshots, which may include email addresses and other profile data. The service code uses only friend-request/friendship UIDs, FCM tokens and notification preferences for its notification logic; email is not included in push messages or used to decide whether to send them, but the complete document is still received and loaded in the microservice process. Invalid or unregistered FCM tokens are removed.

7.2 Firebase Crashlytics

Crashlytics collection is disabled by default and is activated only after the user expressly chooses to share technical reports in the initial consent screens or in Settings. The choice and its timestamp are stored in the private profile. If the user declines or withdraws consent, collection is disabled and unsent local reports are deleted. When enabled, Crashlytics may receive stack traces, exception type, Crashlytics Installation UUID, Firebase Installation ID and device information. The app's reporter redacts the original exception message before recording it. Diagnostics are optional and are not required to use the app. Google states a 90-day retention period for stack traces and associated identifiers before removal from active systems and backups. The controllers must verify the applicable ePrivacy requirements and the final legal basis before publication.

7.3 Firebase App Check and Google Play Integrity

App Check helps verify that requests to configured Firebase services originate from an authorised app/device. Development builds use the Debug provider; Android Release builds use Play Integrity. Attestation material is sent to the relevant attestation provider and an App Check token accompanies requests to services where App Check is configured. App Check states that it does not retain the attestation material. Tokens have a configurable time to live of up to seven days and, without replay protection, are not retained by Firebase services after use. The Play Integrity provider applies its own terms and privacy information.

App Check is configured only for selected Firebase services and is not user authentication. The separate quiz backend controls access through a Firebase Authentication ID token in the Bearer header, which it validates including token revocation and disabled-account status. The server also applies per-IP and per-UID rate limits. App Check is not the authentication or access-control mechanism for the quiz backend.

9. Transfers outside the European Economic Area

Some providers are established in the United States or use global infrastructure. Google states that Firebase Authentication operates from data centres in the United States, while Firestore, Crashlytics, App Check and FCM may be processed on Google's global infrastructure unless a specific applicable data-location option has been selected by the customer. Groq states that customer data for GroqCloud services is stored in Google Cloud buckets in the United States. For Stadia tile requests, the app uses EU endpoints that connect clients to servers in the European Union; Stadia also states that it scrubs personal data at the network edge. This does not guarantee that every internal processing activity by Stadia or its sub-processors takes place exclusively in the EU: Stadia's DPA allows Customer Data to be processed in any country where Stadia or its sub-processors operate and provides Standard Contractual Clauses for restricted transfers. The relevant documents and transfer mechanisms of the other providers apply separately.

For transfers to the United States, providers may rely on the EU–US Data Privacy Framework (DPF) adequacy decision where the receiving entity is certified and the processing falls within the certification's scope. In other cases, the European Commission's Standard Contractual Clauses (SCCs) and any supplementary safeguards required by the GDPR may apply. The actual mechanism depends on the contracting entity and the service involved. Users may request information about the safeguards applicable to transfers concerning their data.

The quiz backend and notification microservice are hosted on the school infrastructure associated with pascal.ispascalcomandini.it. Quiz requests terminate TLS at Nginx; container-to-container communication takes place over a private Docker network.

Further information: Italian Data Protection Authority – international transfers · European Commission – Standard Contractual Clauses.

12. Minors

The service is limited to people aged 14 or over. Before Google Sign-In, users declare that they are at least 14. Under-14s may not register or use the service. This is a self-declaration: the app does not request or collect date of birth and does not verify age using identity documents. The private profile stores a server-generated timestamp and version identifier for the age policy confirmed. It also stores the timestamp and version of the accepted Terms and acknowledged Privacy Notice. These records document the confirmations made in the app but do not verify the user's actual age or identity using documents. In Italy, Article 2-quinquies of Legislative Decree 196/2003 sets 14 as the age for a child's consent to processing for directly offered information-society services where consent is the legal basis; it does not automatically grant full contractual capacity.

13. Security, website and automated processing

The project uses Firebase Authentication, Firestore security rules, App Check for configured Firebase services, Play Integrity in Android Release builds and HTTPS.
