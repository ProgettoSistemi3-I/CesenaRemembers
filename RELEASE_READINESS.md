# Pre-release readiness checklist

This file contains operational checks that cannot be completed by editing repository files alone. Do not treat the release as ready until every applicable item is confirmed.

## Privacy, legal roles and minors

- [ ] Finalise and retain the Article 26 GDPR joint-controller arrangement in a private project archive. The public Privacy Notice must make the essence of the arrangement available to users; the full internal agreement does not need to be published.
- [ ] Ensure the joint-controller arrangement is validly accepted and signed by both controllers, following the applicable Italian civil-capacity and representation rules. Keep the executed copy in a private archive, not in this public repository.
- [x] Record the current school infrastructure arrangement: the Istituto Superiore Pascal - Comandini provides a dedicated Raspberry Pi and network connectivity; based on the operators' statement, only the two controllers have ordinary administrative access to the application server, databases and application logs. The school is not appointed as an Article 28 processor for the arrangement as described. Reassess before any school access, backup, maintenance or processing on behalf of the controllers.
- [ ] Review the legal bases stated in the Privacy Notice. In particular, document the legitimate-interest assessment for searchable profiles, social functions, leaderboard visibility, abuse prevention and account moderation.
- [ ] Approve or change the moderation-record retention period. The implementation assigns a 24-calendar-month `retentionUntil` to `banned_users`; the record stores UID, reason and `bannedAt` and is intentionally not removed by normal account deletion. Schedule `scripts/purge_expired_bans.py --apply` (for example daily via cron) only after the retention period has been approved. Records subject to a legal hold must have `legalHold: true`. Legacy records without `retentionUntil` are reported and left untouched until they are reviewed/backfilled.
- [ ] The app now applies a 14+ access policy: before Google Sign-In, users must accept the Terms, acknowledge the Privacy Notice and declare that they have completed 14 years of age. Test that Google Sign-In cannot start while either checkbox is clear. The declaration is self-reported and is not documentary age verification; the app does not collect date of birth. This policy excludes under-14 users and does not provide a parental-authorisation route.
- [ ] In Google Play Console, set the target audience and age groups to match the actual product and the 14+ onboarding policy. Complete Families/children declarations where applicable, content rating and privacy-policy URL.
- [ ] Complete and document the ePrivacy/GDPR assessment of optional Firebase Crashlytics collection (Crashlytics Installation UUID, Firebase Installation ID, stack traces and device information). Verify the final legal basis and privacy-policy wording before release. Test that collection remains off by default, starts only after explicit opt-in, that a refusal leaves the app fully usable, and that withdrawal disables collection and deletes unsent local reports.
- [ ] Verify the explicit FCM opt-in flow. Notifications are off for accounts without a recorded consent flag and server timestamp; test first activation, OS permission denial, revocation, legacy accounts and token deletion.
- [ ] Complete Play Console Data Safety using the final build. Specifically disclose that GPS coordinates are sent to Mapbox Directions automatically during an active tour when the user's position changes by about 40–45 metres or the destination changes. Review the data-sharing declarations for Mapbox and map-tile providers, plus account identifiers, profile data, app activity, diagnostics, device identifiers and push tokens.
- [ ] Verify that Italian and English legal pages are deployed and that login and Settings open the version matching the app language.
- [ ] Verify that the public account-deletion pages and the in-app deletion flow are available and tested: `https://cesenaremembers.com/legal/delete-account.html` and `https://cesenaremembers.com/legal/delete-account-en.html`.

## Deployment and credentials

- [ ] Restrict the Android Firebase API key in Google Cloud Console: set the Android application restriction to package `it.cesenaremembers.app` and the correct Play App Signing SHA-1 certificate; restrict the key to the APIs actually required by the shipped Firebase/Google SDKs. Verify that the production key and any development keys have separate, appropriate restrictions.
- [ ] Deploy the updated Firestore rules and committed indexes with `firebase deploy --only firestore:rules,firestore:indexes --project cesenaremembers1945`. Confirm the leaderboard query succeeds on a clean project after index creation and the new notification-consent fields pass the deployed rules.
- [ ] Enable Firebase App Check enforcement for each production Firebase service used by the app only after validating Android Play Integrity with the Play App Signing identity. A debug provider/token is not a production verification.
- [ ] Place the Firebase Admin service-account key at `server_docker/notifier-service/serviceAccountKey.json` on the server only. It is excluded from Docker build context and is mounted read-only into the notifier container; never commit it or bake it into the image.
- [ ] From `server_docker`, validate the Compose configuration and start the notifier with `docker compose up -d --build notifier-service`. Confirm the container remains healthy and its logs do not contain credential or permission errors.
- [ ] Verify that the certificate mounted for Nginx is the same certificate bundled at `assets/certs/server.crt`. The app trusts that certificate specifically; certificate replacement requires a coordinated app update and server deployment. Check validity/expiry and test the public endpoint at `https://pascal.ispascalcomandini.it:8000`.
- [ ] Schedule the moderation-retention cleanup using a protected service account with read, update and delete access to `banned_users`; test the dry-run and legacy backfill output before enabling `--apply`.
- [ ] Confirm Docker log rotation is active on the target host. Compose configures at most three 10 MB JSON log files for each service container; host-level logs and external reverse-proxy logs need their own policy.
- [ ] Keep the quiz container on the dedicated `quiz-backend` Docker network shared only with Nginx. Do not publish the Uvicorn port on the host or attach unrelated containers to that network while `FORWARDED_ALLOW_IPS=*` is configured.

## Functional and security tests

- [ ] Verify FCM auto-initialization and Analytics collection are disabled in the Android manifest. Confirm no FCM registration token/installation identifier is generated or uploaded before the in-app opt-in and Android notification permission are both granted.
- [ ] Test notifications for incoming friend requests and accepted requests with the app foregrounded, backgrounded and terminated. Confirm English and Italian content follows the stored profile language.
- [ ] Test GPS recovery on a physical Android device: revoke location permission while the app remains open, restore it in system settings, return to the app and confirm the shared position stream resumes without force-closing.
- [ ] Test disabling notifications, force-closing/restarting the app, then receiving another request. No token should remain registered for a disabled user and no push should be sent.
- [ ] Test FCM token refresh and pruning of invalid/unregistered tokens. Verify the user's `fcmTokens` array remains at or below the Firestore Rules limit of 20.
- [ ] Run Firestore Rules tests for all account, profile, friend-request, leaderboard, friend-statistics and moderation flows. Confirm every rules branch remains under the Firestore expression-evaluation limit.
- [ ] Run the required `public_profiles` migration against a backup/controlled dataset before deploying the rules that depend on it.
- [ ] Verify Firebase App Check enforcement and Play Integrity using the actual Play signing configuration, not only a debug build.
- [ ] Confirm the GitHub Actions validation job is green for the exact commit to be released: it runs `flutter pub get`, `flutter gen-l10n`, `flutter analyze`, the complete `flutter test` suite and `node --check` on the notifier. Also produce and verify the signed release artifact. Also validate `docker compose config`, build the notifier image and test the deployed backend.
- [ ] Confirm that the APK/APK release artifact hosted on GitHub and the Google Play listing correspond to the same reviewed release.
